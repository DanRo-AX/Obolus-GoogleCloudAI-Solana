## 1. 이번 대화에서 확정된 제품 정의

Obulus는 범용 LLM이 알기 어려운 실제 사람의 지역·직군·도메인 경험을 검색하고, 질문에 필요한 근거만 마이크로페이로 열어 데이터 소유자에게 정산하는 인간 경험 데이터 네트워크다.

핵심 가치는 다음과 같다.

1. 사람의 답변을 일회성 설문 결과로 소모하지 않는다.
2. 답변을 출처·시점·동의·버전이 있는 개인 메모리 문서로 축적한다.
3. 다음 질문에서 동일한 실제 경험이 필요하면 다시 검색한다.
4. 검색과 비교는 무료로 제공하고, 실제 원문 근거를 열 때만 결제한다.
5. 기존 근거가 부족하면 질문자가 대상·답변 수·보상을 정한 공개 모집을 연다.
6. 채택된 답변은 현재 질문을 해결하고 이후 질문에 다시 사용되는 데이터 자산이 된다.

제품을 다음과 같이 설명하지 않는다.

- 단순 설문 플랫폼
- 합성 페르소나 생성기
- 평균적인 사람의 반응을 지어내는 시뮬레이터
- 모든 요청을 곧바로 설문 모집으로 전환하는 서비스
- 사용자의 지갑 개인키를 중앙 서버가 보관하는 결제 서비스

## 2. 구매자와 기여자에게 전달해야 하는 가치

### 구매자

구매자는 대규모 패널을 처음부터 모집하지 않고도 이미 축적된 실제 경험을 검색할 수 있다. 질문과 관련된 후보 DB의 메타데이터, 가격, 최신성, 신뢰도는 결제 전에 비교한다. 필요한 독립 근거만 열기 때문에 전체 패널 비용을 지불하지 않는다.

기존 근거만으로 충분하지 않을 때에만 공개 모집을 제안한다. 공개 모집은 자동 fallback이 아니라 사용자가 대상, 필요 인원, 답변당 보상과 마감을 확인한 뒤 선택하는 별도 조사 방식이다.

### 기여자

기여자는 한 번 제공한 구체적인 경험을 자신의 개인 DB에 축적한다. 같은 문서가 이후 질문에서 실제로 열릴 때마다 다시 정산받을 수 있다. 원문의 버전과 동의 범위, 수취인 지갑, 판매 이력이 함께 관리되어야 한다.

## 3. 검색과 공개 모집의 최종 흐름

```text
자연어 질문
→ Gemini/Vertex AI가 대상·지역·분야·조건·예산을 구조화
→ 기존 개인 DB의 무료 메타데이터 검색
→ 관련성·최신성·신뢰도·질문별 권위·저자 다양성 평가
→ 동일 저자와 중복 문서 제거
→ 질문에 필요한 최소 독립 근거 묶음 선택
→ 정확한 가격과 결제 범위 계산
→ 선불 잔액 안에서 문서별 x402/Pay.sh 정산
→ 결제된 passage만 Gemini에 전달
→ 출처가 있는 답변과 청구서 제공
```

기존 근거가 부족한 경우:

```text
근거 부족 감지
→ 무료 일반 답변 또는 기존 근거로 가능한 범위 제시
→ 사람의 답이 꼭 필요한 부족 부분을 명확히 설명
→ 사용자에게 공개 모집 선택지 제시
→ 사용자가 대상·답변 수·답변당 보상·마감 확정
→ 기여자 참여와 후속 인터뷰
→ 품질 검증 및 채택
→ 기여자 정산
→ 개인 DB에 버전형 문서로 축적
→ 현재 답변 및 이후 검색에서 재사용
```

## 4. 검색·랭킹에 관한 확정 설명

Obulus는 전체 DB를 매 요청마다 완전 탐색하거나 전역 인기순으로 나열하지 않는다.

대규모 DB에서는 다음 두 단계를 구분한다.

1. 후보 검색
   - 구조화 필터
   - 텍스트 검색
   - 개체·희귀 단어 일치
   - 규모가 커지면 벡터 임베딩 기반 ANN 검색을 후보 생성 단계에 추가
2. 최종 랭킹
   - 질문 관련성
   - freshness
   - 작성자 및 문서 신뢰도
   - 질문별 Personalized PageRank
   - 독립 검증 관계
   - 동일 저자·중복 내용 감점
   - 가격과 예산

벡터 임베딩은 PageRank의 대체재가 아니다. 임베딩은 의미가 가까운 후보를 빠르게 찾고, Personalized PageRank는 질문과 근거 그래프를 기준으로 어떤 후보를 더 신뢰할지 계산한다.

유료 관계, 자기 추천, 복제 문서와 광고 관계는 긍정 권위를 만들지 못해야 한다. 결제는 사용 기록을 남기지만 권위를 구매하지 않는다.

## 5. Gemini와 에이전트 자율성

Gemini/Vertex AI는 다음을 담당한다.

- 질문의 의도와 대상 조건 해석
- 필요한 도구와 조사 단계 선택
- 기존 근거의 충분성 판단
- 부족한 인간 근거 식별
- 기여자에게 물을 후속 질문 생성
- 결제되고 허용된 근거만 사용한 최종 합성

Rust 및 결정론적 서비스는 다음을 통제한다.

- 동의와 문서 버전
- 가격과 수취인
- 검색·랭킹 정책
- 결제 가능 범위
- 실제로 열린 문서 목록
- 중복 결제 방지
- 인용 allowlist
- 청구서와 복구 원장

평가 기준상 강조해야 하는 자율성은 단순 LLM 답변 생성이 아니라 `계획 → 도구 선택 → 검색 → 근거 평가 → 결제 방식 결정 → 합성`의 다단계 실행이다.

## 6. 현재 확인된 Phantom → Pay.sh 결제 구조

### 결론

현재 브라우저 결제 경로에는 Phantom에서 KMS가 관리하는 Pay.sh 서비스 지갑으로 Devnet USDC를 충전하는 로직이 있다.

정확한 흐름은 다음과 같다.

```text
Phantom 연결
→ 지갑 소유권 확인용 메시지 서명
→ 제한된 선불 세션 생성
→ 질문에 필요한 근거 묶음과 부족 금액 계산
→ 잔액이 부족한 경우에만 Phantom이 정확한 USDC 충전을 승인
→ OPENSHELF_BUNDLE_RECEIVER로 Devnet USDC 전송
→ 백엔드가 payer·payTo·금액·network·memo 검증
→ 선불 원장에 반영하고 질문 예산 예약
→ Pay.sh/KMS 에이전트가 선택 문서별 정산
→ 기여자 지갑과 프로토콜 몫 기록
→ 청구서 및 온체인 증명 제공
```

### Phantom에서 사용자가 누르는 승인

Phantom에는 두 종류의 서명이 존재한다.

1. 로그인/세션 메시지 서명
   - 지갑 소유권만 증명한다.
   - 자금은 이동하지 않는다.
2. 선불 잔액 충전 트랜잭션 서명
   - 잔액이 부족한 경우 Phantom 팝업에서 사용자가 실제 USDC 전송을 컨펌한다.
   - 이미 선불 잔액이 충분하면 문서 하나를 열 때마다 Phantom 컨펌을 반복하지 않는다.

### 요청마다 새 지갑이 생기는가

아니다. 요청마다 새로운 온체인 Pay.sh 가상지갑이나 개인키를 생성하지 않는다.

기본적으로 동일한 KMS 서비스 지갑을 계속 사용한다. 요청마다 달라지는 것은 다음 기록이다.

- 결제 견적과 bundle ID
- 결제 memo와 idempotency key
- 질문별 선불 금액 예약
- 열린 문서와 수취인 목록
- 문서별 Pay.sh 정산 기록
- 트랜잭션 증명과 청구서

선불 세션이 만료되어 새 세션 원장 항목이 만들어질 수는 있지만, 이는 데이터베이스상의 제한형 회계 세션이지 새로운 Solana 주소나 개인키가 아니다.

### 자동 결제의 경계

사용자는 모든 문서 결제를 매번 승인하지 않는다. 최초 충전 또는 추가 충전만 Phantom에서 승인하고, 이후 Pay.sh 에이전트는 이미 충전된 선불 잔액과 질문별 한도 안에서만 자동 결제한다.

서버가 할 수 없는 일:

- Phantom 개인키 열람
- 사용자가 서명하지 않은 Phantom 잔액 임의 출금
- 견적보다 큰 금액을 Phantom에서 가져오기
- 결제 전 원문 passage 공개

서버가 수행하는 일:

- 서명된 충전 거래 검증
- 선불 원장 반영
- 질문 예산 예약
- 문서별 Pay.sh 정산
- 중복·실패·부분 복구 처리
- 청구서와 감사 로그 생성

## 7. 결제 주소 구성에서 남은 확인 사항

코드와 문서가 의도하는 운영 구조는 아래 두 환경 변수가 동일한 KMS 제어 지갑을 가리키는 것이다.

- `OPENSHELF_BUNDLE_RECEIVER`
- `OPENSHELF_PAY_OPERATOR_WALLET`

저장소의 `.env.example`에는 실제 주소가 아닌 placeholder만 존재한다. 따라서 라이브 Cloud Run 배포의 실제 주소 동일성은 저장소만으로 증명할 수 없다.

상용화 전 필요한 보완:

1. 시작 시 두 운영 주소의 동일성 또는 허용된 관계 검증
2. 네트워크와 USDC mint allowlist 고정
3. quote의 수취인·금액·만료·memo 서버 서명
4. 중복 settlement와 replay 방지
5. 질문별·일별·사용자별 한도
6. 청구서에서 충전과 실제 문서 사용을 분리 표시
7. 사용하지 않은 선불 잔액 환급 정책
8. Mainnet 전 독립 보안 감사

## 8. 청구서 UX에 관한 최종 요구사항

매 결제를 Phantom에서 수동 승인하게 만들지 않는다. 대신 사용자가 언제든 확인할 수 있는 별도 `청구서` 버튼과 탭을 제공한다.

청구서에는 다음 정보가 필요하다.

- 질문 및 research bundle ID
- 결제 시각과 상태
- Phantom payer 주소
- KMS service wallet 주소
- network와 USDC mint
- 충전 승인 금액
- 실제 사용 금액과 남은 선불 잔액
- 열린 문서 ID·버전·콘텐츠 해시
- 문서별 가격
- 각 데이터 소유자의 수취인 주소
- 기여자 몫과 프로토콜 몫
- x402 payment proof
- Solana transaction signature와 Explorer 링크
- 중복 방지 key
- 실패·복구·환불 상태

영수증은 축하용 confetti UI보다 감사 가능성과 가독성이 우선이다. 온체인 증명과 내부 원장 기록의 차이를 명확히 표시해야 한다.

## 9. 중앙 서버 신뢰를 줄이는 구조

중앙 서버는 질문 계획, 검색, 원장, 복구를 담당하지만 다음 경계로 임의 결제를 제한한다.

- Phantom 개인키는 브라우저 지갑 밖으로 나오지 않는다.
- 서비스 운영키는 Cloud KMS의 비수출형 키로 관리한다.
- 모델은 결제 수취인과 금액을 직접 작성하지 못한다.
- 서버는 사전 생성된 canonical quote만 실행한다.
- Pay.sh가 처리할 수 있는 URL, network, asset, recipient를 allowlist로 제한한다.
- 각 결제는 memo, bundle, 문서 버전, 수취인과 연결된다.
- 동일 작업 재시도 시 같은 idempotency key로 중복 지급을 막는다.
- 청구서와 Solana 기록을 사용자가 직접 대조할 수 있어야 한다.

블록체인은 원문의 진실성을 자동으로 보장하지 않는다. 누가 어떤 문서 버전을 열었고 누구에게 얼마가 정산됐는지를 변조하기 어렵게 남기는 역할을 한다.

## 10. Web과 Local/MCP 버전의 구분

### Hosted Web

- 사용자는 Pay.sh를 별도로 설치하지 않는다.
- Phantom은 소유권 확인과 선불 USDC 충전에 사용한다.
- Cloud Run과 KMS Pay.sh 운영 지갑이 자동 정산한다.
- 일반 사용자와 라이브 데모에 적합하다.

### Local Agent / MCP

- Claude, Codex 등 로컬 에이전트가 Obulus 검색과 결제 도구를 호출한다.
- 사용자의 로컬 Pay.sh 설치 또는 앱에 번들된 Pay.sh가 필요할 수 있다.
- 로컬 키와 정책으로 exact-intent 결제를 수행한다.
- 브라우저의 재사용 선불 세션과 달리 one-shot exact bundle 결제 경로를 사용할 수 있다.

두 버전은 선택지이며, Hosted Web 사용자가 로컬 Pay.sh를 반드시 설치해야 하는 구조로 만들지 않는다.

## 11. 데이터 콜드 스타트에 관한 결정

SNS 최신 트렌드 수집, X API, Obsidian, mem0 연동은 핵심 피치와 현재 HTML에서 제외하기로 했다. 제품 범위를 넓히기보다 초기 신뢰 가능한 인간 DB 공급을 만드는 문제에 집중한다.

콜드 스타트 권장 경로:

1. 검증 가능한 전문·지역 커뮤니티와 제한된 도메인으로 시작
2. 공인된 공개 질문과 허가된 공개 데이터로 초기 검색 corpus 구성
3. 공개 데이터는 인간 firsthand evidence와 명확히 구분
4. 실제 기여자가 답한 데이터에는 출처·시점·동의·지갑을 연결
5. 첫 구매 수요를 공개 모집으로 전환하되 자동 게시하지 않음
6. 채택·재사용·신고·결과 검증을 신뢰 신호로 축적
7. 신원 인증은 답변의 진실성 보장과 구분

## 12. 기본 AI 답변과 인간 근거의 관계

Obulus는 인간 DB가 없다는 이유로 모든 기본 답변을 차단하지 않는다.

권장 응답 계층:

1. 일반 지식이나 공개 웹으로 답할 수 있는 부분은 무료 baseline으로 답한다.
2. 실제 인간 경험이 없는 부분은 추측하지 않고 근거 공백을 표시한다.
3. 기존 Obulus 문서가 있으면 가격과 출처 메타데이터를 먼저 제시한다.
4. 결제된 인간 원문만 유료 evidence로 인용한다.
5. 공개 모집은 인간 답변이 정말 필요한 경우 사용자가 선택한다.

## 13. 대시보드·채팅·화이트페이퍼 UI 최종 방향

전반적인 디자인 원칙:

- OpenAI 제품처럼 흰 여백, 명확한 계층, 절제된 선과 그림자
- 불필요한 외곽선과 AI 템플릿 느낌 제거
- 검정·흰색을 기본으로 하고 일부 카드에만 불규칙한 유체형 색상 사용
- 제목 강제 줄바꿈과 이상한 들여쓰기 금지
- 카드 hover 시 들썩이는 translate 효과 금지
- hover shadow는 약 2~3px의 어두운 그림자로 0.2초 전환
- 화면 중앙의 좁은 고정 폭을 모든 페이지에 강제하지 않음
- 데스크톱에서는 사이드바를 제외한 실제 콘텐츠 폭을 적극 활용
- toggle/popover는 바깥 영역 클릭 시 닫힘
- 드롭다운은 viewport 바깥으로 잘리지 않도록 위·아래 위치 자동 결정

### 설문 참여 `/dashboard`

- 원래의 밝은 카드와 유체형 이미지 스타일 유지
- 좌측 카테고리 전용 보조 사이드바 제거
- 상단에 카테고리·검색·정렬을 한 줄의 절제된 필터로 배치
- 카드 이미지는 반복되는 단순 gradient가 아니라 불규칙한 광택·섬유 질감 사용
- 카드 hover 시 이동하지 않고 그림자만 부드럽게 변경

### 미답변 주제 `/coverage`

- 설문 참여 카드 디자인을 그대로 복사하지 않음
- 페이지 상단은 폭을 충분히 사용하는 검정 hero
- 오른쪽에 투명 배경의 Obulus 3D wordmark/리서치 비주얼 배치
- hero 높이와 문장을 컴팩트하게 유지
- 분야 카드는 한 행 3개
- 카드의 검정 overlay는 너무 어둡지 않게 완화
- 카드 하단에 별도의 딱딱한 검정 설명 블록을 두지 않음
- hover 시 배경 이미지 zoom과 상세 정보/행동이 자연스럽게 나타남
- 아직 열린 질문이 없는 분야도 현재 상태를 명확히 표시

### 질문하기와 채팅

- Obulus 질문, 검색, 랭킹, 근거 선택과 추가 조사 선택이 하나의 에이전트 흐름으로 보여야 함
- 일반 Codex/Claude처럼 tool calling과 research progress를 이해할 수 있게 표시
- 답변은 실시간 streaming
- 범위 선택은 나이·지역·동거인·분야를 태그형 multi-select로 제공
- 선택 popover는 바깥 클릭 시 닫힘
- 인간 근거가 부족해도 공개 모집으로 자동 전환하지 않음
- 추가 조사는 선택 사항이며 가격·대상·답변 수를 먼저 설정

### 내 문서 `/memory`

- 프로필, 내 답변과 수익, 내 질문, 거래/청구서 탭을 명확히 구분
- Phantom 연결 이후 접근 가능
- 실제 Phantom의 Devnet USDC 잔액을 RPC로 조회해 표시
- 내 질문 목록은 큰 회색 박스 반복 대신 제목, 상태, 사용 금액, 열린 문서 수 중심으로 정리
- 별도 청구서 탭 또는 버튼 제공

### 화이트페이퍼 `/whitepaper`

- 전체를 검정 카드로 만들지 않음
- 핵심 강조 문장만 검정 배경과 큰 흰 글씨로 사용
- 파이프라인 표는 흰색 행 기반의 읽기 쉬운 목록으로 유지
- 기술 flow diagram은 원래의 밝은 배경으로 유지
- 실제 terminal 예시는 macOS/CLI 창처럼 헤더·prompt·상태가 자연스럽게 보이도록 구성
- 추상적인 선언보다 검색→랭킹→결제→누적을 구체적으로 설명

## 15. 이번 대화의 최근 원문 문답

### 사용자

> 지금 phantom에서 pay.sh 지갑으로 옮겨지는 로직이 있나?

### 답변 요지

> 있다. 정확히는 Phantom 개인키나 지갑 자체를 이동하는 것이 아니라, 잔액이 부족할 때 Phantom이 x402의 정확한 Devnet USDC 충전 거래를 서명하고 `OPENSHELF_BUNDLE_RECEIVER`인 KMS 서비스 지갑으로 전송한다. 백엔드는 거래를 검증해 선불 원장에 반영하고, 이후 Pay.sh/KMS 에이전트가 실제로 열린 문서별로 기여자에게 정산한다. 배포 환경에서 `OPENSHELF_BUNDLE_RECEIVER`와 `OPENSHELF_PAY_OPERATOR_WALLET`이 의도한 동일 운영 지갑인지 확인이 필요하다.

### 사용자

> 팬텀이 서명한다는건 내가 팬텀에서 컨펌 누른단거지? 그리고 요청마다 pay.sh 가상지갑이 매번생기는것도 아닌거고

### 답변 요지

> 맞다. 최초 로그인은 자금 이동 없는 메시지 서명이고, 실제 선불 충전이 필요할 때 Phantom 팝업에서 USDC 전송을 직접 컨펌한다. 잔액이 충분하면 문서마다 Phantom 확인을 반복하지 않는다. 요청마다 Pay.sh 지갑도 새로 만들지 않으며, 동일한 KMS 서비스 지갑을 사용한다. 요청마다 새로 생성되는 것은 quote, bundle ID, 원장 예약, 문서별 정산 내역과 청구서다.
